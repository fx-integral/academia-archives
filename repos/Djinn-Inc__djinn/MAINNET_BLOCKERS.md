# Mainnet Launch Blockers

**Mission:** zero the P0/P1 list. Cross-verify via Codex and multi-iteration Claude audits. Launch on Base mainnet with real USDC only when this doc has no P0/P1 items and three independent audit passes agree.

**Rules:**
- P0 / P1 block launch. P2 is strongly recommended. P3 is post-launch.
- Every item has an **Owner** (me = autonomous, human = user), a **State**, and a **Verification** line describing how we know it's fixed.
- Autonomous loop edits this file. Items added as discovered, removed (or moved to "Closed") when verified.
- Before launch, **at least one /codex-audit pass and two Claude fresh-eyes passes must agree the doc is empty of P0/P1.**
- Never downgrade severity without explicit user sign-off.

Severity legend:
- **P0** = protocol can lose user funds or permanently break if launched as-is
- **P1** = protocol is operationally fragile; launch would be reckless
- **P2** = launch is feasible but rough
- **P3** = polish

Status legend: `open` | `in-progress` | `verifying` | `closed`

### P1-37 · Validators vote on different batchKeys due to per-validator audit_set subset divergence (NEW 2026-05-03)
- **State:** open
- **Owner:** me + protocol
- **What:** Each validator's `audit_set_store` is populated by its own bootstrap iteration (now parallelized via v1675/v1678 BOOTSTRAP_CONCURRENCY but still per-validator). Validators with different bootstrap progress on the same `(genius, idiot)` pair see different SUBSETS of purchase_ids. Example post-2026-05-03 stress-scale on `(G0, 0x8E734344)`: UID 1 saw 2 of 10 signals, UID 2 saw 2 of 10 (different subset), UID 213 saw 10 of 10. Each builds `batchKey = keccak(g, i, keccak(its_pids))` → THREE DIFFERENT batchKeys → each casts 1 vote into its own bucket → no quorum can ever form.
- **Observed evidence:** UID 213 voted on (G0, 0x4B4cBa66) full-10 batchKey at block 41020829 (tx 0xf84f326d, sepolia.base.org RPC). publicnode RPC missed the event (separate P1: RPC indexing inconsistency, fixed in watchdog). Other validators had different subsets of the same pair → no other VoteSubmitted events for the same batchKey across 50k blocks.
- **Risk on mainnet:** even with all upstream fixes (shadow_settle, bootstrap speedup, game_date determinism, BPA/WPA replication) and 5-of-5 honest validators, quorum never forms because they vote on different batchKeys. The protocol's settlement layer is fundamentally blocked by per-validator subset divergence.
- **Fix candidates:**
  - **(a) Canonical purchase_id source.** Have validators read the canonical PID list for `(g, i, cycle)` directly from chain (`Account.getPairPurchaseIds`) at vote time, not from their local audit_set. Their local set may have a subset, but they vote on the canonical full list. build_pi remains gated on having enough local data; for missing data, validator must pull from peers (P1-33 BPA/WPA reliability) or abstain entirely.
  - **(b) Subset-tolerant quorum.** Change OV.submitVote to allow voting on a "subset of purchase_ids" with a max-vote-count tie-breaker that picks the LARGEST subset that 4-of-5 agree on. Complex; risk of attacker-controlled subset selection.
  - **(c) Bootstrap convergence guarantee.** Validators wait until their bootstrap is "complete" (matches on-chain canonical event count) before voting. Slow but deterministic.
- **Verification:** after fix, observe 4-of-5 validators voting on the SAME batchKey within one settlement cycle.

- **State:** code-complete (M1 shipped 2026-04-24 as v1596+v1597; M2+M3 reverted 2026-04-24 as v1603 per "build simpler" reframe); pending timelock-upgrade deployment + `setActiveWindow` activation

When 2/3 of current signers propose the same new set, the contract atomically replaces it. So the self-healing is architecturally in place.
- **What's actually broken (2 gaps):**
  - **(Gap A) Bootstrap deadlock when >1/3 of signers are offline.** `proposeSync` requires 2/3 of the *current* set (4 of 6) to agree. Present state: UID 0 (v1590, running sync), UID 2 (v1592+1, running sync), UID 86 (v1592+1, running sync) = 3 validators in agreement. UID 189 (Kooltek68) offline entirely. UID 1 (RoundTable21) stuck at v1586 — may not be running the sync loop at all; even if it is, its proposed set may differ. UID 213 (TAO.com) on hardcoded v999 — unknown whether sync runs. Live+aligned = 3; threshold = 4; set cannot update from within the active fleet. Every P0-01 stall since 2026-04-21 traces to this deadlock, not to plumbing bugs.
  - **(Gap B) No cost to cheat.** `proposeSync` has no bond, no stake, no challenge period — it is pure liveness. A validator can vote for a wrong outcome on `submitVote` with zero on-chain consequence. The miner reputation + collateral machinery on the other contracts does NOT apply to validator voting. User wisdom 2026-04-23: **"if cheating benefits them, validators WILL cheat."** Gasper, Tendermint, and every production BFT system defend against this with slashing; Djinn currently does not. This is the deeper mainnet risk, beyond mere liveness.
- **Risk on mainnet:** (a) liveness — Gap A means one offline operator with margin=0 halts settlement fleet-wide (current state); (b) safety under cheating — Gap B means an operator or coalition voting for an economically-favorable wrong outcome faces zero on-chain consequence. Rejected stake-weighted voting (Bittensor-native Yuma-style) as the fix because SN103 stake concentrates among 2–3 top delegates; 67% of stake = 2–3 colluders, which is *easier* to corrupt than 4 of 6 uniform-weight signers, not harder. Lazy-validator problem compounds. Bittensor's Yuma works for emissions because no one cares enough to collude; Djinn moves real USDC, so incentive to cheat is much higher. Ethereum's Gasper uses BFT-with-slashing for exactly this reason.
- **Chosen design (2026-04-23):** additive UUPS upgrade to OutcomeVoting adding (1) emergency force-sync escape hatch, (2) validator vote-bond + slashing, (3) fraud-proof challenge window. KEEP existing 1-validator-1-vote uniform-weight semantics. KEEP existing `proposeSync` self-healing path as the primary mechanism; force-sync is a safety valve, not a replacement.
- **Implementation plan (final, 2026-04-24):**
  - **Milestone 1 — liveness-aware quorum. ✅ SHIPPED v1596 + v1597 (2026-04-24).** Additive UUPS upgrade to OutcomeVoting adding `lastActiveBlock[validator]`, `activeWindow` config, `heartbeat()` fn, `activeCount()` view, `isActive(addr)` view, and modified `submitVote` + `quorumThreshold` to snapshot active count (floored at MIN_VALIDATORS=3). Validator-side heartbeat loop shipped in v1597 (`validator/djinn_validator/main.py::heartbeat_loop`).
  - **Milestone 2 (vote bonding) and Milestone 3 (oracle fraud proofs) — REVERTED in v1603 (2026-04-24).** Briefly shipped in v1598+v1599+v1601+v1602 but reconsidered. The "validators will cheat" threat model assumed we needed BFT-with-slashing on top of Bittensor. But SN103 validators already have TAO stake at risk via Yuma consensus — a validator that votes divergently loses emissions. Adding an independent USDC bonding + ECDSA-oracle-signed fraud-proof system was layering crypto-economic defenses on top of an already-defended layer, with significant added complexity (≈770 LoC, 52 tests, 8 deployment scripts, multi-sig oracle trust vector). User directive 2026-04-24 ("it shouldn't be that complicated; just a bunch of validators agreeing on game outcomes") crystallized that we were overengineering. - **Verification:** `voting.activeWindow()` writeable by owner, `heartbeat()` emits `ValidatorHeartbeat`, `quorumThreshold()` reflects active set under liveness-on. ### P1-39 · v1682 deterministic-coordinator-selection capped votes at 1 per pair (REVERTED 2026-05-03)
- **State:** closed (reverted in v1683)
- **Owner:** me
- **What:** v1682 attempted to fix the P1-38 collision-loop hypothesis by gating shadow_settle to only run on the lowest-x validator in each participant set.
